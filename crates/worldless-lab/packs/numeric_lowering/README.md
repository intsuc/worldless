# Numeric lowering data pack

This pack compares three lowerings for a bounded signed-integer dot product
without physical-world state.

## Contract

Each public entry point reads `worldless_lab:numeric_lowering/input`. The
input must contain exactly these fields:

```snbt
{a:[I;...],b:[I;...]}
```

Both fields must be `IntArrayTag` values of the same length. The accepted
lengths are 1, 4, 16, and 64, and every element must be between -128 and 127
inclusive. Invalid input returns failure with value 0 before replacing work
state or updating public output.

For input length `N`, one kernel computes:

```text
dot = sum(a[i] * b[i], i = 0 .. N - 1)
```

A public call runs that same kernel 63 times. The checksum starts at 1 and,
after each kernel result, uses signed 32-bit wrapping arithmetic:

```text
checksum = checksum * 31 + dot
```

The element bounds and maximum length prove that every product and dot product
fits in signed 32 bits. A successful invocation sets the `checksum` field in
`worldless_lab:numeric_lowering/output` and returns success with value 1. The
lab clears output storage before each invocation, so its checked output is
exactly `{checksum:<IntTag>}`.

The public entry points are:

- `worldless_lab:numeric_lowering/scoreboard_unrolled/run`;
- `worldless_lab:numeric_lowering/compute_fused/run`;
- `worldless_lab:numeric_lowering/compute_chunked/run`.

## Lowerings

`scoreboard_unrolled` loads every fixed storage path into score holders and
uses scoreboard multiplication and addition. `compute_fused` evaluates all
products and their sum as one inline integer number-provider expression.
`compute_chunked` evaluates at most 16 products per number-provider sum and
combines multiple chunk results with scoreboard addition. It is intentionally
identical to the fused lowering through width 16; width 64 is the case that
separates the two compute tree sizes.

The common validation path uses width-specific integer `minimum` and
`maximum` number-provider expressions after checking the exact fields, array
types, and lengths. This range proof is part of the contract, not incidental
test data. Minecraft integer number-provider sum and product overflow behavior
does not implement arbitrary wrapping-i32 expressions, so the compute
lowerings must not be generalized to unrestricted i32 operands from this
experiment.

All kernels use statically generated fixed paths. The drivers statically
unroll the 63 kernel calls and use one shared checksum fold, avoiding dynamic
indexing, function-macro cache behavior, result-array growth, and
variant-specific output work. Command quota counts a compute command as one
command regardless of the size of its provider tree, so elapsed time, command
quota, generated byte size, and longest command line are separate results.
Pack loading and compilation remain outside the comparison timer.

## Generated code size

The runtime pack payload (`pack.mcmeta` and `data`, excluding this README) is
167,099 bytes and contains 35 function resources. The following counts only
nonblank command lines in the four width-specific kernel resources for each
variant; the shared validation, drivers, fold, and output code are excluded.
Longest-line measurements are ASCII bytes excluding the newline.

| Variant | Width 1 | Width 4 | Width 16 | Width 64 | Total | Longest line |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Scoreboard unrolled | 3 | 15 | 63 | 255 | 336 | 114 |
| Compute fused | 1 | 1 | 1 | 1 | 4 | 12,756 |
| Compute chunked | 1 | 1 | 1 | 7 | 10 | 3,274 |

Thus fused compute minimizes kernel lines and command quota by placing a much
larger provider tree on one source line. Chunking bounds that line growth at
the cost of extra compute/store and scoreboard-add commands once the width
exceeds 16. These sizes describe the generated pack; pack loading and parsing
are not included in the invocation timings below.

## Measurement

From the repository root, run correctness and persistent comparison with:

```sh
cargo run -p worldless-lab -- check --suite numeric_lowering --format text
cargo run --release -p worldless-lab -- compare --suite numeric_lowering \
  --execution persistent --warmup 1 --samples 31 --format text
```

## Sample results

### Worldless

The persistent command above produced these results on 2026-08-31 on an AMD
Ryzen 9 9950X3D running Linux 7.0.0-29-generic with rustc 1.98.0. Each cell is
`quota; median`, with median time in microseconds. Times are
environment-dependent.

| Width | Scoreboard unrolled `quota; median` | Compute fused `quota; median` | Compute chunked `quota; median` |
| ---: | ---: | ---: | ---: |
| 1 | 631; 119.810 | 442; 84.740 | 442; 85.321 |
| 4 | 1,765; 336.431 | 442; 99.190 | 442; 99.390 |
| 16 | 6,301; 1,184.614 | 442; 155.560 | 442; 158.211 |
| 64 | 24,445; 3,517.801 | 442; 299.241 | 1,009; 390.622 |

At width 64, fused compute used 98.2 percent less command quota and had a 91.5
percent lower median than scoreboard unrolling. It also had a 23.4 percent
lower median than 16-term chunking in this Worldless run. Through width 16 the
fused and chunked kernels are identical, and their measured medians remained
close. Fused quota stayed at 442 as width grew because provider-tree nodes do
not consume command quota individually, while its median still rose from
84.740 to 299.241 microseconds. These results support full fusion for this
bounded, storage-backed dot product in Worldless; they do not establish the
same choice for unrestricted wrapping i32 arithmetic, longer command lines,
other expression shapes, or Minecraft runtime performance.

### Minecraft Java Edition

The same inputs and entry points were checked and measured on Minecraft Java
dedicated server `26.3-snapshot-10` on 2026-08-31. The host was the same Ryzen
9 9950X3D running Linux 7.0.0-29-generic. The server used Microsoft OpenJDK
25.0.1+8-LTS, `-Xms2G -Xmx2G`, `--nogui`, and no players. The server JAR
SHA-256 was
`cdbbda7cc47e026e57be8e10d9ef097ad16f1086b63b88a469a4c0e6e4f77dbe`,
and the Java executable SHA-256 was
`75ca070bd7f7e3ae53441509f25483951ec20a0ef42aef6a2dc8ea02531b3952`.

Minecraft's stopwatch has 1 ms resolution, so a sample was an unrolled batch
of `R` consecutive public calls. Calibration selected a power-of-two `R`
toward 100 ms while keeping `R` times the Worldless quota below 800,000. For
some rows, the quota rule or the maximum `R` of 1,024 kept batches below the
preferred 50 ms floor. For every row, each of two fresh JVMs discarded 20
warm-up batches and measured 15; the second JVM traversed all rows in reverse
order. The table pools the 30 unfiltered batch averages. Each cell is
`R; median / nearest-rank p95`, in microseconds per call.

Input installation, calibration, the single-call preflight, and all result
checks were outside the stopwatch. Every preflight returned 1 and produced
exactly the expected output without extra fields. Every measured batch ended
with the expected public checksum and matching internal result checksum. The
two JVMs recorded 197 and 185 young collections, no full collection, and
maximum pauses of 49.484 and 50.245 ms. Samples were not filtered, so pauses
inside timed batches remain in the results.

| Width | Scoreboard unrolled `R; median / p95` | Compute fused `R; median / p95` | Compute chunked `R; median / p95` |
| ---: | ---: | ---: | ---: |
| 1 | 1,024; 50.293 / 58.594 | 1,024; 47.852 / 57.617 | 1,024; 48.828 / 49.805 |
| 4 | 256; 144.531 / 148.438 | 1,024; 63.477 / 67.383 | 1,024; 63.477 / 65.430 |
| 16 | 64; 500.000 / 531.250 | 1,024; 125.488 / 129.883 | 1,024; 125.000 / 130.859 |
| 64 | 32; 1,968.750 / 2,000.000 | 512; 364.258 / 376.953 | 512; 435.547 / 449.219 |

At width 64, fused compute had an 81.5 percent lower Minecraft median than
scoreboard unrolling and a 16.4 percent lower median than 16-term chunking.
The equivalent fused and chunked kernels remained close through width 16.
This target therefore also favored full fusion within the tested 12,756-byte
maximum line, while chunking retained the smaller source-line bound shown
above. The result does not locate a crossover for wider expressions or the
target's command-length limit.

Both runtimes used persistent warm state, but their absolute times are not
paired latencies. Minecraft measures batches in a server JVM with a 1 ms
clock, while Worldless measures individual invocations with its host clock;
the runtime implementations and row-order controls also differ. Comparisons
should remain within each runtime.

## Failure boundaries

Input validation was checked separately with missing and extra fields, wrong
NBT types, mismatched or unsupported lengths, and values immediately outside
the accepted range. Those failures returned 0 without changing pre-existing
work or output state.

Command-limit interruption is not a validation failure and does not roll back
mutations. The width-64 scoreboard row used Worldless quota 24,445. A direct
invocation with that exact limit reported `CommandLimitExceeded` even though
the checksum had already reached both internal and public output; 24,446
succeeded. At limit 100, interruption occurred after work initialization,
leaving its checksum at 0 while preserving the old public output. A subsequent
full-limit call on the same VM succeeded because `prepare` replaced that work.
The execution status, rather than apparently complete output, is authoritative
at a quota boundary.

A separate fresh Minecraft JVM interrupted the width-64 chunked entry after
100 commands. Its result store remained at 0, no expected public checksum was
present, and the surrounding `execute store` did not replace its return-value
sentinel. Restoring `minecraft:max_command_sequence_length` to 1,000,000 and
rerunning on the same server produced the exact result. Failure probes were
kept outside the timing and GC samples above.
